# What the pages say about writing Rust well

Each line names the page that states it. Read the page before relying on the line in a review. The choices we make on top of these pages, for the machine and for agents, are in the Rust section of the coding-rulebook skill in this plugin (`runtime-engineering:coding-rulebook`); check Rust work against it too.

## Ownership and data

- Borrow by default; a `clone` is the visible cost of a copy, and one added to satisfy the borrow checker is the bug, not the fix. https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html
- A struct that holds a reference carries a lifetime and cannot outlive the data; a compiler suggestion of `'static` usually marks a dangling reference to fix. https://doc.rust-lang.org/book/ch10-03-lifetime-syntax.html
- `Option<T>` where a value may be absent; the compiler forces the `None` case. https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html
- Each unit of measure is a newtype; mixing two is a compile error, and an alias gives no protection. https://doc.rust-lang.org/book/ch20-03-advanced-types.html and https://rust-lang.github.io/api-guidelines/type-safety.html
- `Rc<RefCell<T>>` checks borrows at run time, panics on a conflict and is single-threaded; `Arc<Mutex<T>>` for shared state across threads. https://doc.rust-lang.org/book/ch15-05-interior-mutability.html and https://doc.rust-lang.org/book/ch16-03-shared-state.html
- Box a large array or a large enum variant; values over about 128 bytes copy through memory, and a spawned thread's default stack is currently 2 MiB on Tier-1 platforms, platform-dependent, subject to change and set by `Builder::stack_size` or `RUST_MIN_STACK`. https://nnethercote.github.io/perf-book/type-sizes.html and https://doc.rust-lang.org/std/thread/index.html

## Errors

- `Result` is the default; `?` converts through `From` into the crate's error enum. https://doc.rust-lang.org/book/ch09-02-recoverable-errors-with-result.html
- A library's error type implements `std::error::Error + Send + Sync`, with `source()` for a wrapped cause; `()` is never an error type. https://rust-lang.github.io/api-guidelines/interoperability.html and https://doc.rust-lang.org/std/error/trait.Error.html
- A binary's `main` returns `Result<(), Box<dyn Error>>`. https://doc.rust-lang.org/book/ch12-03-improving-error-handling-and-modularity.html
- `unwrap` and `expect` belong in tests, examples and `main`; every library path returns the error. coding-rulebook R14 is the rule: it exempts test-only code and `main`, nothing else. The workspace lints deny both, and `clippy.toml` allows them in tests. https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html
- `Result` is `#[must_use]`; mark a pure function or a builder type `#[must_use]` too. https://doc.rust-lang.org/std/result/index.html and https://doc.rust-lang.org/reference/attributes/diagnostics.html
- A destructor never fails or blocks. https://rust-lang.github.io/api-guidelines/dependability.html
- The release profile sets `panic = "abort"`, which ends the process on a panic without running any destructor; `Drop` cannot be what keeps on-disk state correct. https://doc.rust-lang.org/cargo/reference/profiles.html
- One `enum Error` per crate with a `From` for each wrapped cause; never `Result<_, String>`. https://rust-lang.github.io/api-guidelines/interoperability.html
- A stub returns the crate's error through `not_built("<task>")`, never a panic; the task that fills a stub fills only its own stubs. https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html

## Numbers

- Integer overflow panics in a debug build and wraps in release by default; our release profile keeps `overflow-checks = true` (a 3.5% geomean cost on Rust benchmarks), and a trap aborts the process, so at a boundary use `checked_`, `saturating_` or `wrapping_` operations on purpose. A proven kernel opts out with `[profile.release.package.<kernel>] overflow-checks = false`, explicit `wrapping_*` inside it and the measured delta in MAP.md; a crate that parses outside bytes never opts out. https://doc.rust-lang.org/book/ch03-02-data-types.html, https://doc.rust-lang.org/cargo/reference/profiles.html#overflow-checks and https://mktrm.github.io/files/int_overflow_usenix26.pdf
- `sin`, `cos`, `powf` and `exp` vary by platform and version; `sqrt`, `mul_add`, `floor` and the arithmetic operators are correctly rounded, so deterministic but not exact (`0.1_f64 + 0.2 == 0.3` is false, rustc 1.99.1). A result that must match across browser and server uses the deterministic set in one operation order, or a tolerance; fixed point only where the contract needs it. https://doc.rust-lang.org/std/primitive.f64.html
- Iterators are zero-cost and remove bounds checks that an index loop pays. https://doc.rust-lang.org/book/ch13-04-performance.html and https://nnethercote.github.io/perf-book/bounds-checks.html

## Traits and the public face

- Generics for a homogeneous collection, monomorphized; `dyn Trait` for a heterogeneous one, paying a lookup. https://doc.rust-lang.org/book/ch18-02-trait-objects.html
- Private fields, `pub use` re-exports from the crate root, sealed traits where a trait must not be implemented outside; keep the `pub` surface small. https://rust-lang.github.io/api-guidelines/future-proofing.html and https://doc.rust-lang.org/book/ch14-02-publishing-to-crates-io.html
- Names: `snake_case` functions and modules, `UpperCamelCase` types, `SCREAMING_SNAKE_CASE` constants; `as_`, `to_`, `into_` conversions by cost; no `get_` prefix. https://rust-lang.github.io/api-guidelines/naming.html
- Derive `Debug`, `Clone`, `PartialEq` and the rest eagerly, our choice from the guidelines, except `Debug` on a type holding a secret or an environment, which writes its own; keep types `Send` and `Sync` where possible. https://rust-lang.github.io/api-guidelines/interoperability.html
- Keep items private and widen with `pub(crate)` first. https://doc.rust-lang.org/reference/visibility-and-privacy.html
- Never return `impl Trait` across a crate boundary, our choice, not the compiler's: the caller gets a type it cannot name, and can store only through inference or a generic; return a named type. https://doc.rust-lang.org/reference/types/impl-trait.html and https://rust-lang.github.io/api-guidelines/future-proofing.html

## Crates and modules

- A package holds at most one library crate and any number of binaries; `main` parses arguments and calls the library's `run`. https://doc.rust-lang.org/book/ch07-01-packages-and-crates.html and https://doc.rust-lang.org/book/ch12-03-improving-error-handling-and-modularity.html
- A workspace shares one `Cargo.lock` and one `target/`; each member declares its dependencies, and Cargo refuses a cycle. https://doc.rust-lang.org/book/ch14-03-cargo-workspaces.html
- Module files are `src/garden.rs` with `src/garden/vegetables.rs`; `mod.rs` only under `tests/common/`. https://doc.rust-lang.org/book/ch07-05-separating-modules-into-different-files.html
- Features are additive; an optional dependency is `dep:name`; a `std` feature adds std, and no feature removes it. https://doc.rust-lang.org/cargo/reference/features.html
- Every module starts with a `//!` line saying what belongs there and what does not. https://doc.rust-lang.org/book/ch14-02-publishing-to-crates-io.html
- Every dependency is declared once in `[workspace.dependencies]` and members use `x.workspace = true`; a path dependency carries its `version`; a git dependency is pinned to a `rev`. https://doc.rust-lang.org/cargo/reference/workspaces.html and https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html

## Where builds live

- Never share a target dir (`CARGO_TARGET_DIR`, `--target-dir`, `build.target-dir`) between two checkouts. Cargo judges freshness by file times, so a checkout whose broken file is older than the other checkout's build reports `Finished` and passes broken code. Each worktree builds in its own `target/`, removed when the work ends. https://doc.rust-lang.org/cargo/reference/build-cache.html and https://doc.rust-lang.org/cargo/reference/config.html
- The workspace `Cargo.toml` sets `[profile.dev] debug = "line-tables-only"` and `[profile.dev.package."*"] debug = 0`: our crates keep file:line backtraces, dependencies carry no debug info, which makes a cold target smaller and its build faster. The dependency override has no environment variable, so it lives in the manifest. https://doc.rust-lang.org/cargo/reference/profiles.html
- A build that runs once (a gate before landing, CI) sets `CARGO_INCREMENTAL=0`; a build loop iterating on a change keeps incremental on. Incremental output adds to a target, though rustc deletes each crate's obsolete session folders and keeps only the newest; Cargo removes none of the other artifacts a `target/` gathers. With incremental off, an edit rebuilds slower. Cargo 1.99 turns incremental off itself when `CI` is set. https://doc.rust-lang.org/cargo/reference/config.html, https://doc.rust-lang.org/nightly/nightly-rustc/rustc_incremental/persist/fs/index.html and https://doc.rust-lang.org/nightly/cargo/CHANGELOG.html
- Each `tests/*.rs` file is its own linked binary. A package with many integration tests sets `autotests = false` and keeps one test crate, `tests/it/main.rs` with a module per file; tests that share one process must not depend on environment variables, globals or the working directory. https://doc.rust-lang.org/cargo/reference/cargo-targets.html
- Don't add sccache to make a second checkout cheaper before measuring it: each target keeps its own copies of what the cache returns, so the target is no smaller, and clippy-driver isn't cached. The levers are the profile above, incremental off, and removing `target/` when the work ends. https://github.com/mozilla/sccache

## Fast tests

- Time the build apart from the run before touching profiles or compilers: `cargo test --no-run` times the build alone, and the minutes are often test runtime, not compile.
- A test of a deliberately unreachable pool sets a short acquisition deadline (100 ms); the production deadline is proved in its own test.
- Measure lock contention before raising test parallelism or narrowing a shared lock: a narrower lock can make the suites slower.
- Checks and proofs build the same packages with the same features, so a proof never rebuilds what the check built.
- Batch small per-file work into one process, keeping every input and every failure.
- A test whose subject is time keeps its real timers and sleeps; shorten only waits that test something else.
- While editing, run the focused test binary (`cargo test -p <crate> --test <name>`); run the full gate once on the final commit.

## Async and threads

- The standard library ships no async runtime; choose one only for an I/O-bound crate. https://doc.rust-lang.org/book/ch17-01-futures-and-syntax.html
- A blocking call inside `async` stops the thread; CPU-bound work runs on threads. https://doc.rust-lang.org/book/ch17-02-concurrency-with-async.html and https://doc.rust-lang.org/book/ch17-06-futures-tasks-threads.html

## Unsafe

- `unsafe` lives inside a safe abstraction, stays small, and every block carries a `// SAFETY:` invariant naming the alignment, bounds, aliasing, lifetime and thread assumptions it rests on, never `checked above`. Which crates may use it is coding-rulebook R12; how each is proven is under Close to the machine. https://doc.rust-lang.org/book/ch20-01-unsafe-rust.html and https://doc.rust-lang.org/nomicon/working-with-unsafe.html
- `std::env::set_var` and `remove_var` are `unsafe` in edition 2024 (E0133 under `deny`); a test of Config takes an injected snapshot or runs a subprocess with `Command::envs`, never a process-wide `Mutex` plus `set_var`. https://doc.rust-lang.org/edition-guide/rust-2024/newly-unsafe-functions.html
- A panic cannot unwind out of `extern "C"`; use `"C-unwind"` where it must. https://doc.rust-lang.org/reference/items/functions.html

## Close to the machine

For a kernel, a parser of outside bytes, a store or a foreign library. Each names its page.

- Unsafe per crate, proven. Which crate may use `unsafe`, how it is listed in MAP.md and marked at its root, and what an exception cites: coding-rulebook R12. The facts under it: a crate cannot allow a lint below `forbid` (E0453), and a member cannot mix `[lints] workspace = true` with its own keys. The proof is `cargo +nightly-<date> miri test -p <crate>` in `ci/proof/miri-<crate>.sh` where the crate has no FFI; by default Miri runs no foreign code, and this standard does not rely on its experimental `-Zmiri-native-lib` flag, so an FFI or intrinsics crate adds a sanitizer-backed fuzz target and a differential test against its scalar twin, complementary and neither alone. standard-check reads the MAP.md list and refuses any other crate-level lint relaxation. https://doc.rust-lang.org/rustc/lints/levels.html, https://doc.rust-lang.org/nomicon/working-with-unsafe.html and https://github.com/rust-lang/miri
- SIMD, stable only, with a scalar twin. `std::simd` is nightly; a kernel uses `std::arch` intrinsics inside `#[target_feature(enable = …)]` functions chosen at run time by `is_x86_feature_detected!` or `is_aarch64_feature_detected!`, never `-C target-feature` for a binary that runs anywhere but the machine that built it. Every SIMD kernel keeps its scalar version beside it and a test that runs both on the same input and on a CPU without the feature (coding-rulebook A5). Before writing intrinsics, read the crate that ships the kernel (memchr, simdutf8, blake3, roaring). https://doc.rust-lang.org/std/simd/index.html, https://doc.rust-lang.org/std/arch/index.html and https://doc.rust-lang.org/reference/attributes/codegen.html
- mmap only over immutable, content-addressed files. A file is mapped only when complete, named by its content hash, opened read-only and never rewritten in place; a file under construction is never mapped. One home (`store`) owns every map and hands out `&[u8]` through a guard that owns it, so a reader outliving the guard is a compile error. A snapshot owner holds each generation: a mapped file is not truncated, rewritten or compacted away while a reader holds it, in this process or another; a new manifest is published atomically and old files stay until every reader releases them. Checksum, format version and structural bounds are checked before any byte is trusted; no `&T` is cast from untrusted bytes without alignment, endianness and validity proofs; authorization is checked before a shared cached result is exposed, even for an identical content hash. https://docs.rs/memmap2/latest/memmap2/struct.Mmap.html
- Benchmarks as a gate, same profile as the ship. Every kernel crate has `benches/` with `harness = false` and criterion; `[profile.bench]` inherits release so the number is the shipped number. Each kernel's budget (ns per item, MB/s per core, allocations and peak live bytes; for a product p50/p95/p99 request ms, throughput, bytes on disk, cancellation ms) lives in `ci/proof/bench-<kernel>.sh` beside a checked-in baseline naming corpus hash, toolchain, CPU, features, thread count and baseline sha. The proof fails only on a regression that reproduces on a second run over a budget agreed before the change and set at no less than 3x the A/A noise floor, measured on the machine that runs the bench and recorded beside the baseline; a noisy sample is not a failure, and a breach under that floor is recorded and backlogged, since criterion's own FAQ says not to rely on CI wall time; a new baseline is reviewed, never reset by the run; a deterministic counter (bytes, items decoded, allocations) is the gate where one exists. It runs on a developer machine before a release, never per push and never in CI; a bench harness does not reproduce `panic = "abort"`, so release-mode behavior is a separate smoke run. https://doc.rust-lang.org/cargo/commands/cargo-bench.html, https://doc.rust-lang.org/cargo/reference/profiles.html and https://bheisler.github.io/criterion.rs/book/faq.html
- Allocation budget, for named steady-state kernels. One `#[global_allocator]` at most, in the root binary, never in a lib or core crate. A kernel MAP.md names (a codec, a tokenizer, a set intersection) is proven allocation-free in steady state by a counting-allocator test in `tests/` after warm-up, not by reading; construction and building allocate, bounded; buffers and arenas are made once per request in app and handed down, with retained capacity capped so one giant input does not grow every worker for good; core takes slices. Persisted and wire formats are flat arrays of explicit integer widths and endianness, never a Rust layout. A counting test complements, and never replaces, workload RSS (coding-rulebook R15). https://doc.rust-lang.org/std/alloc/index.html
- Every parser of outside bytes is fuzzed and bounded. A crate that parses a file format, an archive, markup or its own on-disk format has a `fuzz/` crate with one `fuzz_target!` per entry function, its corpus and crash artifacts checked in, run on a developer machine for a set number of minutes before a release, plus a deterministic malformed corpus in `tests/` (truncated blocks, maximum offsets, malformed lengths) run on both the scalar and the optimized path. Every parser takes its limits as named values (coding-rulebook A2: `max_input_bytes`, `max_expanded_bytes`, `max_zip_ratio`, `max_entries`, `max_depth`, `wall_ms`) and returns `Err` at the limit, ratio and count together since a ratio alone misses tiny or many entries; a run over many files carries an aggregate memory and CPU budget and cancellation; a frame is read under a byte budget, never `read_until` to EOF; signatures, archive paths and every offset and length are checked before allocation or map access; a partial result is explicit, never silent empty output. Our own implementation does not make the input trusted: a parser or FFI crash loses one job in an isolated worker, never the service. https://rust-fuzz.github.io/book/cargo-fuzz/setup.html, https://rust-fuzz.github.io/book/cargo-fuzz/tutorial.html and https://doc.rust-lang.org/std/io/trait.BufRead.html#method.read_until
- Threads for CPU, async at the edge, and nowhere else. CPU work runs on `std::thread::available_parallelism()` threads under bounded work queues, cancellation and one shared CPU budget so nested pools do not oversubscribe, with per-thread state merged after; only the entry crate may depend on an async runtime: `ci/check-lib-imports.sh` refuses tokio, async-std or smol under a lib or core crate, review holds the other layers, and CPU-heavy work never runs on its executor. A reader takes one immutable snapshot swapped by pointer; no shared counter or lock on the read path. `loom` or another bounded model checker only where a custom lock-free or synchronization algorithm is written. https://doc.rust-lang.org/std/thread/fn.available_parallelism.html and https://doc.rust-lang.org/book/ch17-06-futures-tasks-threads.html
- Build for the machine, by profile, measured. `-C target-cpu` and the PGO flags are compiler flags, not profile settings: `target.<triple>.rustflags` in `.cargo/config.toml` passes them for that target in every profile, so set them only for the release build's own command, through `CARGO_TARGET_<triple>_RUSTFLAGS`, named in MAP.md with the bench proof's before and after; a shipped binary is portable with run-time feature dispatch, and `target-cpu=native` only for a binary that runs where it was built. PGO: `-Cprofile-generate`, run the corpus, `llvm-profdata merge`, `-Cprofile-use`, the same flags both builds. https://doc.rust-lang.org/cargo/reference/config.html#targettriplerustflags, https://doc.rust-lang.org/rustc/profile-guided-optimization.html and https://doc.rust-lang.org/std/arch/index.html
- FFI in one adapter crate per foreign library. `extern "C"` declarations with the generated bindings committed, never generated at build (build time is the agent's loop, coding-rulebook G1); every foreign handle owned by a guard whose `Drop` frees it; `"C-unwind"` only where a callback must unwind; one lock when the library is single-threaded; the safe face takes and returns owned Rust types, and no raw pointer crosses the crate boundary. https://doc.rust-lang.org/nomicon/ffi.html and https://doc.rust-lang.org/reference/items/functions.html
- `no_std` kernels, when a real target needs them. A reusable kernel with no I/O that a wasm viewer or an embedded target will carry is `#![cfg_attr(not(feature = "std"), no_std)]` with `alloc`, and `ci/check.sh` runs `cargo check -p <crate> --no-default-features` so the split holds; never on day one, since without std there is no run-time CPU feature detection (memchr), which fights the portable build; the service root, the store, parser workers and async adapters stay `std`, and a workspace is never migrated. MMIO, DMA or interrupt code, if a hardware product ever needs it, carries device-specific volatile, ordering and ownership proofs and hardware tests. https://docs.rust-embedded.org/book/intro/no-std.html and https://doc.rust-lang.org/reference/names/preludes.html#the-no_std-attribute
- Profile with a named tool, in the record. A performance change's record names `perf stat`, `samply` or a flamegraph, criterion's before and after, start-up ms and peak RSS (coding-rulebook A1 and R15), so a reviewer can rerun the claim. https://nnethercote.github.io/perf-book/profiling.html
- Prove it on the real machine. Every done check runs the release binary once against a real, read-only target, since tests can pass while the real binary fails on the machine's own configuration. https://doc.rust-lang.org/cargo/reference/profiles.html
- On-disk formats carry a version byte and golden fixtures of every shipped version, from day one; a reader refuses a version it does not know. https://doc.rust-lang.org/std/io/trait.Read.html
- On-disk state stays correct if the process dies at any line: coding-rulebook R8 says how. Every store has a kill-mid-write test that proves it. https://doc.rust-lang.org/std/fs/struct.File.html#method.sync_all
- Pure kernel crates live in the lib layer with no I/O and no clock; codecs and parsers get proptest round-trips there, and a layer holds as many cohesive crates as its formats need, never one enormous crate or one `Error` spanning the product. https://doc.rust-lang.org/book/ch14-03-cargo-workspaces.html
- Tests run under load. A test passes while cargo runs the rest in parallel; a time-based assert carries a margin or an injected clock. https://doc.rust-lang.org/book/ch11-02-running-tests.html
- Overflow at an untrusted boundary is handled by name, `checked_` or an explicit `Err`, whatever the profile's `overflow-checks` says: a trap aborts, it does not return a parser error. https://doc.rust-lang.org/cargo/reference/profiles.html
- An audited dependency's kernel is preferred to `unsafe` of our own (coding-rulebook R12) where one covers the job: forbidding `unsafe` everywhere only moves it into a dependency we cannot run Miri on. https://github.com/rust-lang/miri and https://arxiv.org/abs/2007.00752
- Nightly is an auxiliary toolchain pinned by date (`nightly-2026-08-17`, as tokio pins its Miri nightly) for Miri and cargo-fuzz only, called `cargo +nightly-<date>` from `ci/proof/`, never the build toolchain, which is the stable pin in `rust-toolchain.toml`, and never floating. https://rust-lang.github.io/rustup/overrides.html and https://rust-fuzz.github.io/book/cargo-fuzz/setup.html
- One portable release build with run-time feature detection; a native profile only for a binary that runs on the machine that built it, named in MAP.md: calling a function compiled with a feature the CPU lacks is undefined behavior, and `target-cpu=native` turns run-time selection off (simdutf8). https://doc.rust-lang.org/reference/attributes/codegen.html#the-target_feature-attribute and https://doc.rust-lang.org/std/arch/index.html

## Tests and docs

- Unit tests in `#[cfg(test)] mod tests` beside the code; integration tests in `tests/` through the public face, helpers in `tests/common/mod.rs`. https://doc.rust-lang.org/book/ch11-03-test-organization.html
- `//!` for a crate, `///` for each public item with Examples, Errors, Panics and Safety sections; doc examples use `?`, and `cargo test` runs them. https://doc.rust-lang.org/book/ch14-02-publishing-to-crates-io.html, https://rust-lang.github.io/api-guidelines/documentation.html and https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html

## Security

- No secret in code, env, argv, output or logs; a secret is named only by where it is stored, and a token is `zeroize`d on drop. https://docs.rs/zeroize/latest/zeroize/
- A child process runs only through one sandbox home: argv and no shell, an env built from nothing, its own process group, wall, idle and output limits, and Drop killing the group; no `Command::new` outside it but in a test fixture named in `catalog/homes.json`. https://doc.rust-lang.org/std/process/struct.Command.html and https://doc.rust-lang.org/std/os/unix/process/trait.CommandExt.html
- A test works in its own temp folder and never touches a real checkout or the real HOME. A child it runs gets an env built from nothing (`env_clear`, then only PATH and what the child needs); a git child also gets a fixture HOME and `GIT_CONFIG_NOSYSTEM`. A real tool is found with the one `find_on_path`, which prints `SKIPPED: <tool> not on PATH`. https://doc.rust-lang.org/std/process/struct.Command.html and https://git-scm.com/docs/git
- The secret scan is the gitleaks CLI with its built-in rules at the installed version (no config file is vendored), `--ignore-gitleaks-allow` and `--log-level error`, any stderr a scanner failure; a working-tree scan reads git's own file list (tracked, and untracked but not ignored), never build output; history and range scans add `--log-opts=--no-textconv --no-ext-diff`; an empty range is clean, and a scanner failure never reads as clean. The invariant is coverage, not the argv: every committed blob and change is scanned, merge resolutions included (a patch log omits a merge's diff without a merge-diff option), which `ci/gitleaks.sh` gets from `--diff-merges=separate`; a test of the scan uses a fixture whose secret exists only in a merge commit, with ignore-file and inline-allow bypass cases and malformed, empty and missing ranges. https://github.com/gitleaks/gitleaks and https://git-scm.com/docs/git-log
- Supply chain: `cargo deny check`, `Cargo.lock` committed, `--locked` everywhere, and a build after `cargo update` runs on a developer machine before each release as the canary, never per push and never in CI. https://embarkstudios.github.io/cargo-deny/ and https://doc.rust-lang.org/cargo/guide/continuous-integration.html

## Ours, with no page behind them

Our Rust standard sets these for every repo; no Rust page states them.

- One home per piece: coding-rulebook G2.
- A new file gets its MAP.md row in the same change.
- A piece's done check is `ci/proof/<name>.sh`, printing `<name>: ok`.
- Precedence when sources disagree: the order the coding-rulebook's Rust section gives.
- Fail closed, proven through the gate: coding-rulebook R17. What this standard adds: a check cannot run when the scanner is missing, its config or index cannot be read, its output is truncated or its report does not parse; in POSIX sh each producer's status is checked on its own, since neither `set -e` nor the last pipeline status proves an earlier stage ran; a failure prints rule and file or a category, never raw scanner output, which may hold the secret.
- Units of measure, in names and at a boundary: coding-rulebook A2.
- A face is frozen once another repo imports it; a shared capability starts as a `lib-*` crate in its first consumer and moves to a shared repo at its second real consumer, as a path change plus a pinned rev with no API change.
