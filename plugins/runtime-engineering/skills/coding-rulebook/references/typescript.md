# The coding rulebook: TypeScript

Read `shared.md` first: it holds the Concepts (C), the rules for all languages (A) and for agents (G), the review bar (B) and the talks cited here by short name. An id starting R is in `rust.md`, one starting P in `python.md`, one starting X in `react.md`, which holds what a React front end adds to these rules.

TypeScript's own facts, page by page, are /ground-typescript's; these are the choices we make with them. Types are erased before the code runs, so every rule here is about what the checker can still see.

**T1. Strict, and stricter than `strict`.** Every tsconfig sets `strict`, `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`; the last two are not in the strict family and catch a missing index and `undefined` written to an optional property. One base tsconfig is inherited (`extends`) by every package and never loosened: no flag removed, no new `skipLibCheck: true`, no looser per-folder config, directly or through a base it extends. Turning a flag off in one package is a finding. Source: https://www.typescriptlang.org/tsconfig/strict.html, https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html, https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html; https://arxiv.org/abs/2504.09246 (about 94% of LLM compile errors in TypeScript are type errors, not syntax).

**T2. No `any`; `unknown`, then narrow.** No `any` in a signature, a cast or a generic argument (`Set<any>`, `any[]`), no bare `Function` type, and no `any` from a library left to flow into our values. A value of unknown shape is `unknown` and is narrowed with `typeof`, `instanceof`, `in` or a type predicate before use. No `as T` except `as const` (use `satisfies` or narrowing), no `as unknown as`, and no postfix `!` outside test files. No `@ts-ignore` or `@ts-nocheck`; `@ts-expect-error` only with its reason, each one reported. A diagnostic is never silenced: when the only fix is one of these or a looser config, a type is wrong, and the builder stops and reports it. Source: https://typescript-eslint.io/rules/no-explicit-any/ ("a dangerous 'escape hatch'"), https://typescript-eslint.io/rules/no-unsafe-assignment/, https://typescript-eslint.io/rules/no-unsafe-function-type/, https://typescript-eslint.io/rules/consistent-type-assertions/, https://typescript-eslint.io/rules/ban-ts-comment/, https://www.typescriptlang.org/docs/handbook/declaration-files/do-s-and-don-ts.html.

**T3. Parse at the boundary, never cast.** Data from outside (a request body, an MCP tool's input, `JSON.parse`, a file, env, argv, a database row, a child process's output, a model's output) enters as `unknown` and gets a type only from code that checks it at run time: a type predicate or a schema validator (zod, or ajv where a JSON Schema already exists), in one place per shape, with the type derived from the schema (`z.infer`), not written beside it. `as T` or `!` on such data is a finding, `JSON.parse(x) as T` included; use `safeParse` where failure is expected. Source: https://www.typescriptlang.org/docs/handbook/2/everyday-types.html ("there is no runtime checking associated with a type assertion"), https://www.typescriptlang.org/docs/handbook/2/narrowing.html (type predicates), https://typescript-eslint.io/rules/no-unsafe-type-assertion/.

**T4. A closed set is a discriminated union, closed by `never`.** Each variant carries a literal `kind`; a `switch` on it covers every member and ends in `default: const _exhaustive: never = x`, so a new member fails the build. Lint `switch-exhaustiveness-check`, which no preset turns on. Source: https://www.typescriptlang.org/docs/handbook/2/narrowing.html (exhaustiveness checking), https://typescript-eslint.io/rules/switch-exhaustiveness-check/.

**T5. Throw `Error`s with a `code` and a `cause`.** Throw only `Error` subclasses; each has a stable `code` and passes its options to `super`, so a rethrow keeps its cause: `class ConfigError extends Error { readonly code = "E_CONFIG"; constructor(message: string, options?: ErrorOptions) { super(message, options); this.name = "ConfigError"; } }`, thrown as `throw new ConfigError("read config", { cause: err })`. Callers branch on `code`, never on `message`. A `catch` variable is `unknown` and is narrowed before it is read. No empty `catch`, and no catch, log and continue (A4). Source: https://nodejs.org/docs/latest-v24.x/api/errors.md ("Use `error.code` to identify an error"; `error.cause`), https://typescript-eslint.io/rules/only-throw-error/; /ground-typescript's Errors rules.

**T6. No floating promises.** Every promise is awaited, returned, or given a rejection handler. A promise left unawaited on purpose still carries its handler (`p.catch(report)`); `void p` with no handler is a finding, whatever its comment says: "Voiding a Promise doesn't handle it or change the runtime behavior." No promise in an `if` or as a callback that expects `void`: no `forEach(async …)`, and no async event handler without its own `try`/`catch`. Source: https://typescript-eslint.io/rules/no-floating-promises/, https://typescript-eslint.io/rules/no-misused-promises/.

**T7. Explicit types at the module face (G3 in TypeScript).** Every exported function and public method names its parameter and return types; nothing exported is inferred. Lint `explicit-module-boundary-types`, which no preset turns on; `isolatedDeclarations` enforces it in `tsc` where a repo also emits declarations. Source: https://typescript-eslint.io/rules/explicit-module-boundary-types/ ("makes it clear… what is the module boundary's input and output"), https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html, https://github.com/microsoft/TypeScript/wiki/Performance ("Adding type annotations, especially return types, can save the compiler a lot of work").

**T8. Check after every edit.** The type checker is in the agent's loop: after each edit the builder runs `tsc --noEmit` on the touched project and reads every diagnostic in full; Node running the file proves nothing, because it strips types and checks none. Types and signatures are written and in context before bodies are. Source: https://nodejs.org/docs/latest-v24.x/api/typescript.md ("no type checking is performed"); https://arxiv.org/abs/2504.09246 (type constraints cut compile errors by more than half and lift repair of non-compiling code 37%); https://arxiv.org/abs/2409.00921 (type definitions in context were "particularly impactful" and error rounds multiplied their effect; mostly in Hazel, repeated in TypeScript); https://arxiv.org/abs/2606.21619 (a constraint that rejects valid programs lowered correctness by up to 97%, so check after writing rather than restrict how the model writes).

**T9. The shared rules, in TypeScript.** A3: no module-level `let` or mutable singleton; pass the clock, config and paths in. A4: no `?? 0`, `|| ""`, `?.` chain ending in a fallback, `catch {}` or `!` standing in for missing data, and no `'unhandledRejection'` listener that does not exit non-zero, since installing one stops Node's default crash (https://nodejs.org/docs/latest-v24.x/api/cli.md, `--unhandled-rejections`); `strict-boolean-expressions` catches `if (count)` on a number. G1: an `interface` or generic needs two implementations; no enums or namespaces (/ground-typescript's `erasableSyntaxOnly`). G6: prefer a typescript-eslint rule or a tsconfig flag to prose. Source: https://typescript-eslint.io/rules/no-non-null-assertion/, https://typescript-eslint.io/rules/strict-boolean-expressions/.

**T10. Brand ids and units that share a primitive.** Two ids, or two measures, that are both `string` or both `number` get distinct branded types (`type UserId = string & { readonly __brand: "UserId" }`), constructed only by the boundary parser (T3), so one cannot be passed for the other. Source: https://www.typescriptlang.org/play/typescript/language-extensions/nominal-typing.ts.html.

**T11. An expected failure is a value.** A failure the caller must handle (not found, invalid input, a refused request) is returned as `{ ok: true; value } | { ok: false; error }`, the repo's one `Result` type (G2). `throw` is for a broken invariant, and is turned into a value or an exit at the process edge. Source: our choice, from A4; https://www.typescriptlang.org/docs/handbook/2/narrowing.html (discriminated unions).

**T12. Nothing blocks the event loop on a serving path.** No synchronous `fs` or `child_process` call, no `JSON.parse` of unbounded input (A8) and no regex built from input on a path that serves requests; CPU work over a few milliseconds goes to a worker thread or a native binary (R15). A CLI and start-up code may be synchronous. Source: https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop, https://nodejs.org/docs/latest-v24.x/api/worker_threads.md.

**T13. A long-lived process is bounded.** It sets a heap bound (`--max-old-space-size`), and every cache and queue has a size cap. Source: https://nodejs.org/docs/latest-v24.x/api/cli.md (`--max-old-space-size`).

**T14. No `node` process per action.** Work done many times runs inside one long-lived process or a batch, not a fresh `node` each time (R15). A CLI imports heavy modules lazily, in the branch that needs them, and turns the module compile cache on. Source: https://nodejs.org/docs/latest-v24.x/api/module.md (`module.enableCompileCache()`).

**T15. A child process takes an argument array, a deadline and a size cap.** `execFile` or `spawn` with an args array, never `exec` or `shell: true` with interpolated input; a `timeout` or an `AbortSignal`; a `maxBuffer` or streamed stdout; `error` and `close` both handled. A non-zero exit is an error value (T11), never ignored. Source: https://nodejs.org/docs/latest-v24.x/api/child_process.md ("Never pass unsanitized user input to this function").

**T16. Streams go through `pipeline`.** Compose streams with `pipeline` from `node:stream/promises`, honor backpressure, and read large input with `for await`, never into one buffer (A8). Source: https://nodejs.org/docs/latest-v24.x/api/stream.md.

**T17. A native binding or install-script dependency is a deployment decision.** A dependency that compiles native code or runs a script at install changes what every machine and build must trust; the builder stops and asks before adding one (G1). Source: https://docs.npmjs.com/cli/v11/using-npm/scripts.

**T18. Install from the lockfile.** `npm ci`, never `npm install`, unless the task is the dependency change itself; never a flag that lets every dependency's install script run. Source: https://docs.npmjs.com/cli/v11/commands/npm-ci.

**T19. ESM, as Node runs it.** Every package is ESM under `nodenext`: relative imports carry their extension, type-only imports use `import type`, `import.meta.dirname` stands in for the CommonJS globals, and there is no `require`. The facts behind each are /ground-typescript's Modules and packages rules. Source: https://nodejs.org/docs/latest-v24.x/api/esm.md, https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html.

**T20. No barrel files; the face is `exports`.** No `index.ts` inside a package that only re-exports. A package's public face is its `package.json` `exports` (G3), and internal aliases use `imports` with `#`, each target naming the emitted file (/ground-typescript's Package face). Source: https://nodejs.org/docs/latest-v24.x/api/packages.md, https://www.typescriptlang.org/docs/handbook/modules/reference.html.

**T21. No circular imports.** A cycle between modules is a finding; break it by moving the shared piece to a module both import. Lint `import-x/no-cycle`, from eslint-plugin-import-x, which /ground-typescript's starting files install and configure. Source: https://github.com/un-ts/eslint-plugin-import-x/blob/master/docs/rules/no-cycle.md ("no resolvable path back to this module via its dependencies").

**T22. One test runner, type-checked tests, real dependencies before mocks.** A repo has one test runner: vitest where it is already present, else `node:test`. Every subtest is awaited, a tsconfig covers the test files, and a test uses a real in-process dependency (PGlite for Postgres, for one) before a mock (A5). Source: https://nodejs.org/docs/latest-v24.x/api/test.md.

**T23. Plain JavaScript (`.mjs`) is held to the same rules.** A Node JavaScript module follows this section as far as JavaScript can express it. ESM only (T19): `node:` specifiers for built-ins, no `module.exports`, no `.cjs` unless the task names one. Types live in JSDoc (`@param`, `@returns`, `@typedef`, `@type`) wherever the repo type-checks JavaScript, written as T2 to T4 ask. A JavaScript file is type-checked only under a tsconfig that sets `allowJs` and `checkJs: true` and includes it, or with `// @ts-check` on its first line; `include` alone checks nothing. The JSDoc rules: no `{*}` or `{any}`, a parsed boundary, closed sets as unions of literal `kind`s. After each edit the builder runs `node --check <file>`, and `tsc --noEmit` where the file is type-checked (T8). Tests run under the repo's one runner (T22). Source: https://www.typescriptlang.org/docs/handbook/jsdoc-supported-types.html, https://www.typescriptlang.org/docs/handbook/intro-to-js-ts.html (`// @ts-check`), https://www.typescriptlang.org/tsconfig/checkJs.html ("Works in tandem with `allowJs`"), https://nodejs.org/docs/latest-v24.x/api/cli.md (`--check`).

## Crash record in TypeScript (A6)

A Node process registers two listeners at start. `process.on('uncaughtExceptionMonitor', (err, origin) => …)` fires before any uncaught exception and leaves Node's default in place: print the stack and exit 1. `process.on('unhandledRejection', (reason) => …)` takes rejections, whose `reason` is an `Error` or any other value: it writes the record with `util.inspect(reason, { depth: 8 })` after redacting it, then calls `process.exit(1)`. Under the default `--unhandled-rejections=throw` Node raises a rejection as an uncaught exception only "if this hook is not set", so once the listener exists it is the listener that must exit non-zero; one that only logs keeps a broken process alive (T9). Each listener writes the record with `fs.writeFileSync`: Node names synchronous cleanup before shutdown as the correct use, and queued async work may never run. Do not resume: Node says "It is not safe to resume normal operation after `'uncaughtException'`", and a process with an `'uncaughtException'` handler exits 0 unless the handler sets `process.exitCode`. The record carries the stack with its `cause` chain. A bundled server ships source maps and starts with `--enable-source-maps`, so the stack names source lines. In a browser, listen for `window` `error` (synchronous throws) and `unhandledrejection` (promises) and send the record. Source: https://nodejs.org/docs/latest-v24.x/api/process.md, https://nodejs.org/docs/latest-v24.x/api/cli.md, https://developer.mozilla.org/en-US/docs/Web/API/Window/error_event, https://developer.mozilla.org/en-US/docs/Web/API/Window/unhandledrejection_event.

## Tool gate in TypeScript

Run in order; stop at the first failure and hand the full output back. In a repo that predates this rulebook, its own CI command is the gate instead (`shared.md`, Existing repos). Each tool is the repo's own: its `package.json` script, or the binary in its `node_modules/.bin`. A tool that is not installed fails the gate; never let `npx` fetch one, since it installs what the project lacks (https://docs.npmjs.com/cli/v11/commands/npx).

1. `node_modules/.bin/tsc --noEmit -p tsconfig.json`, with T1's flags in the tsconfig. https://www.typescriptlang.org/docs/handbook/compiler-options.html
2. `node_modules/.bin/eslint . --max-warnings 0`, extending `tseslint.configs.strictTypeChecked` with `parserOptions.projectService: true`, plus `switch-exhaustiveness-check`, `explicit-module-boundary-types`, `no-unsafe-type-assertion`, `strict-boolean-expressions` and `import-x/no-cycle` (T21) at `error`. Pin the typescript-eslint version: `strict-type-checked` is not semver-stable. https://typescript-eslint.io/users/configs/, https://typescript-eslint.io/getting-started/typed-linting/
3. The repo's test script, which runs its one runner (T22); where the runner is `node:test` and there is no script, `node --test`. Any failing test sets exit code 1. https://nodejs.org/docs/latest-v24.x/api/test.md

## Shared library home in TypeScript

A piece two TypeScript repos need lives in one shared package your organization names and is imported through its `package.json` `exports`, not copied (G2, C4). Where that package keeps a catalog (`catalog/homes.json`), read it before writing a second `Result`, error type, path check, file writer, env reader or schema. Starter files are /ground-typescript's assets.
