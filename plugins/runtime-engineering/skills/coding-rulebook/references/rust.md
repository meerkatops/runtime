# The coding rulebook: Rust

Read `shared.md` first: it holds the Concepts (C), the rules for all languages (A) and for agents (G), the review bar (B) and the talks cited here by short name. An id starting T is in `typescript.md`, one starting P in `python.md`, one starting X in `react.md`.

Rust's own facts, page by page, are /ground-rust's; these are the choices we make with them. R1 to R11 came from the talks `shared.md` lists and R12 to R15 from the papers they cite; R2, R3, R12 and R17 are scoped for kernels, parsers, stores and FFI by /ground-rust's Close to the machine section. Precedence when sources disagree: the user's explicit instruction, then the repo's MAP.md recorded decisions, then this rulebook, then the language's own pages.

**R1. Borrow over clone.** Every `.clone()`, `.to_owned()` and `.to_string()` on a non-`Copy` value has a reason; one added to quiet the borrow checker is a finding. Source: https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html; Rust for AI engineering ("exactly one owner").

**R2. No allocation in a named kernel's steady state.** Inside the hot loop of a kernel MAP.md names (a codec, a tokenizer, an intersection), after warm-up: no `Vec::new`, `String::new`, `format!`, `collect` or `clone`, proven by a counting-allocator test, not by reading. Hoist buffers, `clear()` and reuse them; `with_capacity` when the size is known; don't `collect` into a `Vec` only to iterate it again. Construction and segment building allocate, bounded; an owned copy that crosses a lifetime or thread boundary on purpose is design, not a finding; any other loop is judged by A1's profile. Source: https://nnethercote.github.io/perf-book/heap-allocations.html; Lead architect ("get rid of the heap").

**R3. Read bytes once, in place, under a byte budget.** One read into a buffer, or `BufReader`/`BufWriter`, never many small unbuffered reads. Parse into `&str`/`&[u8]` slices or offsets of that buffer, not owned copies of each field. A frame from outside is read under a per-frame byte budget enforced while reading (`take(max_frame_bytes)` before `read_until`), never `read_until` to EOF: a `Vec` capacity is not a cap. Lock stdout once for repeated writes. Source: https://doc.rust-lang.org/std/io/trait.BufRead.html#method.read_until; https://nnethercote.github.io/perf-book/io.html ("Rust file I/O is unbuffered by default"); Lead architect ("start index… offsets").

**R4. Flat data, indexes for links.** A graph is `Vec<Node>` with `u32` or newtype indexes. No `Rc<RefCell<_>>` webs, no self-referential structs, and an `enum`, not `Box<dyn Trait>`, for a closed set. Source: https://doc.rust-lang.org/book/ch18-02-trait-objects.html, https://doc.rust-lang.org/book/ch15-05-interior-mutability.html; Ronacher ("you can program yourself in the corner"); Torvalds (the cache miss is the unit of cost).

**R5. Know your sizes.** Box a large variant or array. A type on a hot path carries `const _: () = assert!(size_of::<T>() <= N);`, not a comment. Source: https://nnethercote.github.io/perf-book/type-sizes.html; Karpathy, using LLMs (answer size questions by running code).

**R6. An RAII guard for every resource.** Each file, lock, temp dir, child process or lockfile is owned by a value whose `Drop` releases it; no hand-written "remember to close" path. Source: https://doc.rust-lang.org/book/ch15-03-drop.html.

**R7. Drop never fails or blocks.** No waiting, no `unwrap` and no error reported from `Drop`; a close or remove there is nonblocking, bounded and best-effort, its error dropped. Teardown that can fail is a separate `fn finish(self) -> Result<…>`, and nothing relies on `Drop` after an abort. Source: https://rust-lang.github.io/api-guidelines/dependability.html (C-DTOR-FAIL).

**R8. Never rely on Drop for correctness.** `panic = "abort"`, our release profile in /ground-rust's start, runs no destructor on panic; `process::exit`, `mem::forget` and `Rc` cycles skip `Drop` too. On-disk state (locks, journals, half-written files) is safe if the process dies at any line: write a temp file, `sync_all`, rename, `sync_all` the directory (rename is visibility, the syncs are durability), and make what a dead process leaves detectable: locks, temp trees and process groups carry their owner's pid, so the next start sweeps them. The exception is an append-only journal with one writer: `O_APPEND` on a regular file is not a framing guarantee, so each record is checked on read and a torn tail is dropped. Source: https://doc.rust-lang.org/std/fs/struct.File.html#method.sync_all, https://doc.rust-lang.org/std/fs/struct.OpenOptions.html#method.append, https://doc.rust-lang.org/cargo/reference/profiles.html, https://doc.rust-lang.org/std/mem/fn.forget.html ("Rust's safety guarantees do not include a guarantee that destructors will always run").

**R9. No async runtime for a few sequential calls.** No tokio or async-std in a crate whose I/O is a handful of sequential calls; use blocking clients, and threads for parallel work. Source: https://doc.rust-lang.org/book/ch17-01-futures-and-syntax.html, https://doc.rust-lang.org/book/ch17-06-futures-tasks-threads.html; Ronacher (async loses context).

**R10. No hidden work in `Deref`, `From`, `Display`.** `Deref` only on smart pointers, cheap and infallible. `From` is infallible and lossless, else `TryFrom`, and never panics. `Display` only writes to the formatter: no I/O, no locks. Source: https://rust-lang.github.io/api-guidelines/predictability.html (C-DEREF), https://doc.rust-lang.org/std/convert/trait.From.html ("This trait must not fail"), https://doc.rust-lang.org/std/fmt/trait.Display.html.

**R11. The shared rules, in Rust.** G1: no `macro_rules!` that hides control flow, no proc macro of our own. G3: every `pub fn` across a crate boundary names concrete types, with no `impl Trait` return and no inferred error type (https://rust-lang.github.io/api-guidelines/future-proofing.html). A3: no `static mut` and no lazy global with mutable state. A4: no `unwrap_or_default()` or `unwrap_or(0)` for missing data; errors keep `source()`, never a `reason: String` built from `e.to_string()` or a `Result<_, String>` (https://doc.rust-lang.org/std/error/trait.Error.html). G6: prefer a clippy lint or a `[workspace.lints]` entry (https://doc.rust-lang.org/clippy/), and never route around one with a string trick or an `#[allow]`; a rule the code cannot meet is reported, not silenced.

**R12. `unsafe` is denied by default, allowed per named crate, and audited in dependencies.** The workspace sets `unsafe_code = "deny"` (a crate cannot allow below `forbid`: E0453). A crate needing `unsafe` is listed in MAP.md under `## Unsafe crates` with why, carries `#![allow(unsafe_code)]` and `#![deny(unsafe_op_in_unsafe_fn)]` at its root, keeps the `unsafe` behind a safe face in one private module, and carries a `// SAFETY:` invariant per block. A performance exception cites a profile (A1); a boundary exception (OS, FFI, mmap, intrinsics) cites its Miri run or its fuzz target, since a profile proves nothing about soundness. Any other relaxation of a workspace lint is a finding. A new dependency's `unsafe` and FFI are reviewed before it is added. Source: arXiv 2003.03296 (every Rust memory-safety bug to 2020 needed `unsafe`); arXiv 2007.00752 (most unsafety arrives through dependencies); arXiv 2502.15536 (bounds checks cost 56.94% in one kernel, so a profiled exception is allowed); https://doc.rust-lang.org/nomicon/working-with-unsafe.html; https://doc.rust-lang.org/rustc/lints/levels.html; https://github.com/rust-lang/miri.

**R13. Check after every edit.** The builder runs `cargo check` on the touched crate after each edit and reads the full diagnostic, not a summary, before the next edit; then clippy, then tests. People give the skeleton (types and signatures) first. Keep the check fast: small crates, few dependencies (G1). Source: arXiv 2607.13921 Table 1 (Opus 4.8 on the 20 hardest of CRUST-Bench's 100 C-to-Rust tasks: 51.8% of outputs failed to compile with no feedback, 7.5% with compiler feedback after each generation, 2.6% with feedback during it); arXiv 2602.22764 (agents hit about 3 compile errors per task, 32.6% from the type and trait system).

**R14. No panics on library paths.** Outside tests and `main`, no `unwrap()`, `expect()`, `panic!` or unchecked indexing on data from outside; return `Result`. Library crates set clippy `unwrap_used`, `expect_used`, `indexing_slicing` and `panic` to deny. Test-only code may unwrap: `#[test]`, `#[cfg(test)]`, `#[cfg(all(test, ..))]`, a module declared that way, and the crate's `tests/` directory. `#[cfg(any(test, ..))]` and anything under `not(..)` are production code, and removing `#[cfg(test)]` from a `mod` makes its file and every file below it production code. Under our `panic = "abort"` a panic kills the process mid-action (R8). Source: arXiv 2408.03262 (panics are Rust's main run-time failure once memory bugs are gone, centered on `unwrap` and out-of-bounds indexing); https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html; https://doc.rust-lang.org/reference/conditional-compilation.html; https://rust-lang.github.io/rust-clippy/master/.

**R15. One small native binary, start-up and memory measured.** High-volume work ships as one native binary with few dependencies. A change to a hot CLI or engine records its start-up time and peak RSS beside its throughput, with A1's named tool. Work run millions of times stays in a long-lived process or a batch, not a process per action, unless start-up is measured in single-digit ms. Source: arXiv 2609.11932 (Rust's RSS held flat near 7.8 MB under load where Node's RSS grew by 117 MB); arXiv 2410.06145 (cold start is mostly dependency deployment and scheduling); Rust for AI engineering (Copilot start-up 5.25 s to 292 ms).

**R16. Only `main` ends the process.** No `std::process::exit` outside the binary's `main`; library and app code return `Err`, and `main` maps it to an exit code once. `exit` skips every caller's error handling and every `Drop` (R8). Enforced by clippy `exit = "deny"` in `[workspace.lints]`; the lint already exempts `main`, so `main` needs no attribute, and an `#[expect(clippy::exit)]` there fails `-D warnings` as an unfulfilled expectation. Source: https://rust-lang.github.io/rust-clippy/master/index.html#exit. Source: https://doc.rust-lang.org/std/process/fn.exit.html ("no destructors on the current stack or any other thread's stack will be run").

**R17. A child succeeded only if its status says so; a deadline returns `Err`; the gate fails closed.** `Ok(status)` from `Command::output()` or `status()` is not success: check `ExitStatus::success()`, and log the child's stderr as an error only when it failed. A wait with a deadline returns `Err` on timeout, never `Ok`; the deadline is driven while reads block, since a wall checked only after `wait` is no watchdog, and both stdout and stderr are observed. A check that guards an operation (a secret scan, a proof) blocks it when it cannot run, and the test proves that through the gate: it runs the commit, submit or proof command and sees it fail, not only the inner `Err`; a shell pipeline checks each producer's status. Source: https://doc.rust-lang.org/std/process/struct.ExitStatus.html#method.success.

**R18. No shell-outs for file work or privilege.** Never `Command::new("sudo")`, `Command::new("rm")`, `chmod` or `chown`, or a `sudo …` or `rm -rf …` command string; use `std::fs` (`remove_file`, `remove_dir_all`, `set_permissions`). Privilege is the caller's decision, not the library's. `Command::arg` takes a value without shell quotes. Source: https://doc.rust-lang.org/std/fs/index.html, https://doc.rust-lang.org/std/process/struct.Command.html#method.arg.

**R19. Downloads are verified while they stream and installed atomically.** Anything downloaded to run or install is hashed (SHA-256) and its size counted as it streams, hashing only the bytes read (`update(&buf[..n])`), into a temp file in the target directory, and renamed into place only after both match the expected values. Nothing runs before that check. An update replaces by rename and keeps the previous copy for rollback until the new one is proven. Source: https://doc.rust-lang.org/std/fs/fn.rename.html, https://doc.rust-lang.org/std/io/trait.Read.html#tymethod.read.

## Crash record in Rust (A6)

The first statement of `main`, before argument parsing and any logger, calls `std::panic::set_hook`; it is the only `set_hook` in the workspace. The hook writes the record (message, `PanicHookInfo::location`, `std::backtrace::Backtrace::force_capture()`, version, the command with its arguments redacted, the working directory, the names of the environment variables set, context ids, time) with plain blocking `std::io::stderr()` and `std::fs` writes, never through the `log` facade or any logger, then calls the hook it replaced (from `std::panic::take_hook`), so stderr keeps the default message, which prints the panic message as written: a panic message never carries a secret, since A6 redacts only what the record gathers. It writes a crash file even with no console (a GUI, `windows_subsystem`, a daemon): `~/.<binary>/crashes/<time>-<pid>.json`, mode 0600, the last 50 kept. It never panics itself: no `unwrap`, no indexing, every write's error ignored. The hook runs "before the panic runtime is invoked… with both the aborting and unwinding runtimes", so it runs under our `panic = "abort"`, where no `Drop` does (R8). The backtrace needs symbols: the release profile keeps line tables, as /ground-rust's start sets it, or ships split debug info keyed by the version the record carries. An `Err` that `main` returns writes the same record before exit, and logger setup that fails returns such an `Err`; it never panics. Source: https://doc.rust-lang.org/std/panic/fn.set_hook.html, https://doc.rust-lang.org/std/panic/fn.take_hook.html, https://doc.rust-lang.org/std/backtrace/struct.Backtrace.html.

## Tool gate in Rust

Run in order before any model review; each must pass, and the builder fixes what it names (R13). In a repo that predates this rulebook, its own CI command is the gate instead (`shared.md`, Existing repos). `--locked` makes cargo fail rather than rewrite `Cargo.lock`, so the gate judges the dependencies the change committed:

1. `cargo fmt --all -- --check`. https://github.com/rust-lang/rustfmt
2. `cargo clippy --all-targets --all-features --locked -- -D warnings -W clippy::pedantic`: pedantic, denied with every warning. https://doc.rust-lang.org/clippy/usage.html, https://doc.rust-lang.org/cargo/commands/cargo-check.html (`--locked`)
3. `cargo deny check`: advisories, bans, licenses and sources. https://embarkstudios.github.io/cargo-deny/
4. `cargo geiger` where the repo has `ci/geiger-baseline.txt`, else `cargo deny check` and R12's `## Unsafe crates` list: the `unsafe` count in the crate and its dependencies; a count the change raised is reviewed under R12. https://github.com/geiger-rs/cargo-geiger
5. `cargo test --all-targets --locked`. https://doc.rust-lang.org/cargo/commands/cargo-test.html

## Shared library home in Rust

A piece two Rust repos need lives in one shared library repo your organization names and is imported as a cargo git dependency pinned to a `rev`, not copied (G2, C4): its own lib crate, with its own error type and no caller's types. Where that repo keeps a catalog (`catalog/homes.json`), read it before writing anything a second repo could need: running a child, a lock, a clock, an append-only log, git reads, hashing, secret scanning. Starter files are /ground-rust's assets.
