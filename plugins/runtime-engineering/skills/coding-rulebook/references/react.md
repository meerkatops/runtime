# The coding rulebook: React

Read `shared.md` and `typescript.md` first. `shared.md` holds the Concepts (C), the rules for all languages (A) and for agents (G), the review bar (B) and the talks cited here by short name. React code is TypeScript, so every T rule in `typescript.md` holds for it and none is restated here; where a front end differs from a Node package, X21 says how. An id starting R is in `rust.md`, one starting P in `python.md`.

These are the rules for a front end: React, Next.js, CSS, a component library and the tests that prove a page works. The facts behind them, page by page, are /ground-react's; these are the choices we make with them. Where a repo names a design system or brand guidance, follow it for how a page looks; these rules are about how it is built.

**X1. Next.js App Router for an app; React on Vite for a page with no server.** Next.js is React's framework for routing, server rendering and building. A new app with routes, data or sign-in is a Next.js App Router app. A page embedded in another host, or a tool served as static files with no server of its own, is plain React built with Vite. No Pages Router and no hand-made bundler setup in new code. Source: https://react.dev/learn/creating-a-react-app ("we recommend starting with a framework"), https://react.dev/learn/build-a-react-app-from-scratch (starting from scratch "is often the same as building your own adhoc framework").

**X2. Server Components by default; `"use client"` at the leaf.** A component stays a Server Component unless it needs state, an Effect, an event handler or a browser API. `"use client"` goes at the top of the smallest file that needs it, never on a layout or page to quiet an error: everything that file imports joins the client bundle. Props that cross the boundary are serializable. A context or theme provider is a Client Component that takes `children`. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components ("all of its imports and the components it directly renders are included in the client bundle"), https://react.dev/reference/rsc/use-client.

**X3. Data is read on the server, by the component that needs it, through one data layer.** An async Server Component awaits its data. Every read goes through the repo's one server-only data layer, which checks that the caller may see the data and returns only the fields the page shows; a whole record or a secret is never passed as a prop to a Client Component. Independent reads start together, and each slow read sits under its own `<Suspense>`. A Server Component never fetches the app's own Route Handler. In a Client Component, read a promise the server passed with `use`, or use the repo's one fetching library; no `fetch` in an Effect. Source: https://nextjs.org/docs/app/getting-started/fetching-data, https://nextjs.org/docs/app/guides/data-security (the Data Access Layer returns "safe, minimal Data Transfer Objects"), https://nextjs.org/docs/app/guides/production-checklist ("do not call Route Handlers from Server Components").

**X4. A mutation is a Server Function that checks who is calling and what it was sent.** A `"use server"` function can be reached by a direct POST, not only through the page, so each one verifies authentication and authorization itself, parses its arguments as outside input (T3), returns an expected failure as a value (T11) and revalidates what it changed. A form passes it to `<form action>` and reads the result and the pending flag from `useActionState`, never from its own boolean. A Route Handler (`route.ts`) is for a face another program calls, and makes the same checks. Next.js refuses a Server Function called from another site, by comparing `Origin` with `Host`; it does not do that for a Route Handler, so one that takes a browser's POST refuses a cross-site post itself: `Sec-Fetch-Site` must be `same-origin`, or where the browser sends none, `Origin` must name the host. A repo whose mutations already go one way, through Route Handlers called with `fetch`, say, keeps to that way (G2). Source: https://nextjs.org/docs/app/getting-started/mutating-data ("Always verify authentication and authorization inside every Server Function"), https://nextjs.org/docs/app/getting-started/error-handling ("model expected errors as return values"), https://react.dev/reference/rsc/use-server ("always treat them as untrusted input"), https://react.dev/reference/react/useActionState, https://nextjs.org/docs/app/guides/data-security ("Server Actions in Next.js also compare the Origin header to the Host header"; `route.ts` is named among the files to audit), https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-Fetch-Site.

**X5. Caching is said in the code, with its lifetime, and so is a read that must run for each request.** A new app turns Cache Components on. A read that may be shared is cached with `"use cache"` and names its lifetime with `cacheLife`; a cookie or a header is read outside the cached scope and passed in as an argument, so one person's data is never cached under a key another person shares. Caching and prerendering are two things. `"use cache"` is the only thing that caches a read, but whatever can finish at build time is prerendered into the static shell with no directive at all: a module import, a pure computation, and a synchronous read such as `fs.readFileSync` or a query through a synchronous database driver. `<Suspense>` does not change that. So a read that must run for each request, and does not already read `cookies()`, `headers()`, `params` or `searchParams`, awaits `connection()` first. An uncached read sits under `<Suspense>`. A mutation invalidates what it changed. Source: https://nextjs.org/docs/app/getting-started/caching ("We recommend pairing every cache directive with a `cacheLife`"; "module imports, `fs.readFileSync`, and pure computations complete during prerender and are included in the static shell automatically"; "`<Suspense>` … does not itself opt a component into dynamic rendering"), https://nextjs.org/docs/app/api-reference/functions/connection ("Queries from synchronous database drivers like `better-sqlite3` complete during prerendering"; "call `connection()` before your query to exclude them from prerendering"), https://nextjs.org/docs/app/api-reference/directives/use-cache ("To use cookies or headers, read them outside cached scopes and pass values as arguments"), https://nextjs.org/docs/app/getting-started/fetching-data ("`fetch` requests are not cached by default"), https://nextjs.org/docs/app/getting-started/revalidating.

**X6. Components and Hooks are pure, and Hooks are called at the top level.** Rendering changes nothing outside the component: no mutation of props, state or a value already passed to JSX, and no reading of the clock, a random number, `window` or storage during render (A3). Hooks are called only at the top level of a component or a custom Hook. Lint the `recommended` set of `eslint-plugin-react-hooks`, which checks these and reports what the React Compiler cannot compile; disabling one of its rules is a finding, as T2 says of any silenced diagnostic. Source: https://react.dev/reference/rules, https://react.dev/reference/rules/rules-of-hooks, https://react.dev/reference/eslint-plugin-react-hooks.

**X7. An Effect only synchronizes with a system outside React.** No Effect that computes state from props or state, answers a user event, chains state updates, tells a parent about a change or resets state when a prop changes: compute during render, do the work in the event handler, and reset with a `key`. An Effect that subscribes or starts something returns the cleanup that ends it. Source: https://react.dev/learn/you-might-not-need-an-effect ("Effects are an escape hatch from the React paradigm"), https://react.dev/reference/eslint-plugin-react-hooks (`set-state-in-effect`).

**X8. State is minimal and has one owner.** Nothing is kept in state that can be computed from props or other state, and no prop is mirrored into state. State two components share lives in their closest common parent. State a person would expect a link to keep (a filter, a tab, a page number) lives in the URL. Data the server sent is not copied into client state. No state library joins without a task that names it (G1). Source: https://react.dev/learn/choosing-the-state-structure ("Avoid redundant state"; "Don't mirror props in state"), https://react.dev/learn/sharing-state-between-components; the URL rule is our choice, since a link that loses its filter is state held in the wrong place.

**X9. A key is a stable id from the data.** Never the array index for a list that can reorder, grow or shrink, and never a value made during render. Source: https://react.dev/learn/rendering-lists ("Keys must not change"; "Index as a key often leads to subtle and confusing bugs").

**X10. No manual memoization without a measurement.** `useMemo`, `useCallback` and `memo` appear only with a profile that shows the need (A1), or to hold an Effect dependency steady. The React Compiler is stable and memoizes by itself; whether a repo runs it is the repo's config, and code is written by X6 either way so it can be turned on. Source: https://react.dev/learn/react-compiler/introduction ("For new code, we recommend relying on the compiler for memoization").

**X11. Every route has its loading, error and not-found state.** A `<Suspense>` boundary with a fallback that looks like what is coming sits close to each slow read. The app has `app/error.tsx` and `app/global-error.tsx`, and a segment that can recover without the rest of the page has its own `error.tsx`. An error page shows what the person can do, never `error.message`. A missing thing calls `notFound()`. Loading, empty and failed are three different screens (A4). Source: https://nextjs.org/docs/app/getting-started/error-handling, https://nextjs.org/docs/app/api-reference/file-conventions/error, https://react.dev/reference/react/Suspense ("Suspense does not detect when data is fetched inside an Effect or event handler").

**X12. One token file, one styling system.** Every color, space, radius and font is a CSS custom property in one token file, the one theme source, and no other file holds a color literal; `tools/check-tokens.mjs` in /ground-react's starting files refuses one in any source folder: a hex color, a color function, or a named color as the value of a color property. It allows `var(--token)` and a palette key. An app has one styling system: the component library's, or CSS Modules. Tailwind is the one system of a marketing or content site, never a second system inside an app. Global CSS holds only the tokens, a reset and element defaults. The `style` attribute is for a value computed at run time. Source: https://nextjs.org/docs/app/getting-started/css (CSS Modules "locally scope CSS by generating unique class names"; global styles for what is truly global), https://react.dev/reference/react-dom/components/common ("We recommend only using the `style` attribute when your styles depend on JavaScript variables"); one system per app is our rule, with no public source. The reason: two systems are two sources for one spacing or color, and which wins is decided by cascade order, which the component library has to be told about (https://mui.com/material-ui/integrations/nextjs/, `enableCssLayer`).

**X13. Light and dark, by the system setting, and a layout that holds at 390 px.** The token file sets `color-scheme: light dark` and gives each color its dark value under `prefers-color-scheme: dark`; a switch a person can set is an addition, never a replacement. Grid lays out two dimensions and flexbox one. A page works at 390 CSS px wide with no sideways scroll, and no element has a fixed width that breaks it. Motion that is not needed stops under `prefers-reduced-motion`. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-color-scheme, https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme, https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Grid_layout/Basic_concepts, https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Flexible_box_layout/Basic_concepts, https://www.w3.org/WAI/WCAG22/Understanding/reflow.html (320 CSS px without scrolling in two dimensions); 390 px is our floor, the width of the phones we test on.

**X14. MUI is themed once, from the tokens, and imported by path.** Use Material UI for an application's working screens: forms, tables, dialogs and menus whose keyboard and focus behavior it already carries. One `createTheme` call builds the theme with `cssVariables`, and its palette, its `spacing` and its `shape.borderRadius` name the token file's custom properties, so no color, space or radius is written twice. The root layout wraps the app in `AppRouterCacheProvider`, then `ThemeProvider`. `sx` styles one instance, `styled()` a component used again, and the theme's `components` an app-wide change. A color in `sx` is a palette key (`"text.secondary"`), never a literal, and dark styles use `theme.applyStyles("dark", …)`, never a test of `theme.palette.mode`. Import each component from its own path (`@mui/material/Button`), never from the package root and never deeper than one level. All `@mui` packages share one major version. Source: https://mui.com/material-ui/customization/css-theme-variables/usage/, https://mui.com/material-ui/customization/css-theme-variables/native-color/ (a palette value may be `var(--…)`), https://mui.com/material-ui/customization/spacing/ (the theme's `spacing` can be changed), https://mui.com/material-ui/integrations/nextjs/, https://mui.com/material-ui/customization/how-to-customize/, https://mui.com/material-ui/guides/minimizing-bundle-size/ (barrel imports cause "slower startup and rebuild times"), https://mui.com/material-ui/migration/upgrade-to-v7/ ("Deep imports with more than one level are no longer working").

**X15. Accessible by construction.** A native element comes first: a `<button>` for an action, an `<a>` for a place, a `<label>` for every input; ARIA only where no native element does the job. Every control has an accessible name. Everything works by keyboard, and focus is always visible: no `outline: none` without a replacement. Text contrast is at least 4.5:1, and 3:1 for large text and for the edges of controls. A pointer target is at least 24 by 24 CSS px. `<html>` names its `lang`, an image has `alt`, and a change a person must notice is announced (`aria-live` or `role="status"`). Lint the `recommended` set of `eslint-plugin-jsx-a11y`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA (the first rule of ARIA use), https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html, https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html, https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html, https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html, https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html, https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html, https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html.

**X16. Nothing secret reaches the browser, and nothing untrusted reaches the DOM as markup.** No `dangerouslySetInnerHTML` on data we do not own; lint `react/no-danger`, and the one sanctioned use names its sanitizer beside it. A variable reaches client code only with the `NEXT_PUBLIC_` prefix (`VITE_` in a Vite app); it is written into the bundle at build time, so it is never a secret and never a value that differs between deployments of one build. Secrets are read in the data layer (X3) and nowhere else. An app sets a Content Security Policy, and the kind follows from how it renders. An app with Cache Components sends the policy as a header from `headers()` in `next.config.ts`, without a nonce: a nonce needs every page rendered for its request, and Next.js says Partial Prerendering is incompatible with one. That policy allows `'unsafe-inline'` for scripts and styles, since the prerendered shell's inline scripts and the component library's `<style>` elements carry no nonce, and it still closes `object-src`, `base-uri`, `form-action` and `frame-ancestors`. Only an app that renders every page for its request sets a nonce in `proxy.ts`. Source: https://react.dev/reference/react-dom/components/common ("it is trivial to introduce an XSS vulnerability this way"), https://nextjs.org/docs/app/guides/environment-variables, https://vite.dev/guide/env-and-mode, https://nextjs.org/docs/app/guides/data-security ("only the Data Access Layer should access `process.env`"), https://nextjs.org/docs/app/guides/content-security-policy ("Partial Prerendering (PPR) is incompatible with nonce-based CSP"; Without Nonces), https://mui.com/material-ui/guides/content-security-policy/ (Emotion injects `<style>` tags; without a nonce, "`'unsafe-inline'` is the only option").

**X17. Performance is built in and measured.** The least JavaScript reaches the browser (X2). An image goes through `next/image`, with its size known so nothing shifts; a font through `next/font`; a heavy component only the browser needs is loaded lazily; a third-party script through `next/script`. The targets are the Core Web Vitals at the 75th percentile: Largest Contentful Paint within 2.5 s, Interaction to Next Paint within 200 ms, Cumulative Layout Shift within 0.1. A performance change names its measurement (A1). Source: https://web.dev/articles/vitals, https://nextjs.org/docs/app/getting-started/images, https://nextjs.org/docs/app/getting-started/fonts, https://nextjs.org/docs/app/guides/production-checklist.

**X18. A component is tested through the page a person uses; a flow in a real browser.** Vitest with Testing Library tests Client Components and plain logic: find an element by its role and name or its label, act with `userEvent`, and assert what the person sees. No test of state, class names or a markup snapshot, and a test id only where no role or label fits. Async Server Components and whole flows are tested with Playwright against the production build, with role locators and its retrying assertions, at a desktop width and at X13's narrow one, and each flow fails on a console error. Vitest is the repo's one unit runner (T22); Playwright runs flows and is not a second one. Source: https://testing-library.com/docs/queries/about/ (the priority of queries), https://testing-library.com/docs/guiding-principles/ ("The more your tests resemble the way your software is used, the more confidence they can give you"), https://testing-library.com/docs/user-event/intro/, https://nextjs.org/docs/app/guides/testing/vitest ("we recommend using E2E tests for `async` components"), https://nextjs.org/docs/app/guides/testing/playwright ("We recommend running your tests against your production code"), https://playwright.dev/docs/best-practices, https://mui.com/material-ui/guides/testing/ ("We don't recommend snapshot testing").

**X19. A number on screen names its unit, and a missing value looks missing.** A2 in the UI: a quantity is shown with its unit, converted for display from the unit it is stored in, by a function whose name and arguments carry both units; `Intl.NumberFormat` writes the number. A4 in the UI: a value that is absent shows as absent, in words or a dash, never as `0` or an empty cell that reads as a value. Source: A2, A4; https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat/NumberFormat (`style: "unit"`).

**X20. The shared rules, in React.** A3: a component gets its data through props; no module-level mutable state. G1: no wrapper component, higher-order component, context or custom Hook until two callers need it, and no new UI, state, form or fetching library without a task that names it. G2 and C4: before writing a button, dialog, table or form field, search the component library and the repo's components, and use the one that exists. G3: a component's props are an exported `interface` with `readonly` members. G4: one component per file, its test beside it. Source: the rules cited; https://react.dev/learn/thinking-in-react.

**X21. The TypeScript rules, for a bundled app.** T1's flags all hold. The tsconfig sets `module: "esnext"`, `moduleResolution: "bundler"`, `jsx: "react-jsx"` and `noEmit`, so relative imports carry no extension (T19 describes a Node package) and the app has no `exports` face (T20). `skipLibCheck: true` is allowed here, and only here: third-party declaration files do not pass a full lib check, and they are not ours to fix. Seen in /ground-react's starting files: @mui/material 9.5.0 fails `exactOptionalPropertyTypes`, the `.next/types` files Next.js 16.4.6 generates name a `JSX` namespace that is not there, and Vitest 5.1.0 and @testing-library/jest-dom 7.0.1 declare one interface with different type parameters. Next.js apps set `typedRoutes`, so a link to a route that does not exist fails `tsc`. Source: https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html, https://nextjs.org/docs/app/api-reference/config/typescript, https://nextjs.org/docs/app/api-reference/config/next-config-js/typedRoutes; the `skipLibCheck` exception is from /ground-react's starting files, which fail `tsc --skipLibCheck false` with those errors and no other.

**X22. Check after every edit.** T8 holds: `tsc --noEmit` after each edit to a `.ts` or `.tsx` file, every diagnostic read in full. After an edit to a component, the builder also runs that component's test file. A page that renders in the dev server proves nothing about types, the build or a narrow screen. Source: T8 and its sources.

## Crash record in React (A6)

A front end crashes in two places, and each leaves the record A6 describes.

In the browser, `instrumentation-client.ts` runs before the app becomes interactive and listens on `window` for `error` and `unhandledrejection`. An error a boundary catches reaches neither listener, so `app/error.tsx` and `app/global-error.tsx` report what they are handed. Each sends the name, message, stack, cause and the path without its query string to one Route Handler with `navigator.sendBeacon`; when `sendBeacon` returns false, the browser did not queue the report, and a `fetch` with `keepalive` sends it. Before it is sent or written, the message, the stack and the cause are redacted (A6): the value of every URL query parameter, a URL's user and password, a named credential (`password=`, `Authorization:`), a bearer token and any long unbroken run of letters and digits. One budget bounds the whole report: its JSON is at most 16,384 UTF-8 bytes, the stack cut first, and the handler reads no more than that. The handler treats the report as outside input: it refuses a post from another site (X4), caps the body before reading it (A8), checks its shape (T3), redacts and fits it again, since a report can be forged, adds the time and the version, and writes the line. A Vite app, with no server of its own, passes `onUncaughtError` and `onCaughtError` to `createRoot` and sends the record to the host's endpoint.

On the server, `instrumentation.ts` exports `onRequestError`, which Next.js calls for every error it catches while rendering or handling a request; it writes the record with the request path and the error's `digest`, the id the browser is shown in place of the message. `register` runs once at start and, on the Node.js runtime, installs the `uncaughtExceptionMonitor` listener `typescript.md` describes.

The record is one JSON line on stderr (G5). Source: https://nextjs.org/docs/app/api-reference/file-conventions/instrumentation-client, https://nextjs.org/docs/app/api-reference/file-conventions/instrumentation, https://nextjs.org/docs/app/guides/instrumentation, https://nextjs.org/docs/app/api-reference/file-conventions/error (`error.digest`), https://react.dev/reference/react-dom/client/createRoot, https://developer.mozilla.org/en-US/docs/Web/API/Navigator/sendBeacon (it "returns true if the user agent successfully queued the data for transfer. Otherwise, it returns false"); `typescript.md`, Crash record in TypeScript.

## Tool gate in React

Run in order; stop at the first failure and hand the full output back. In a repo that predates this rulebook, its own CI command is the gate instead (`shared.md`, Existing repos). Each tool is the repo's own, as the TypeScript tool gate says; never let `npx` fetch one.

1. `next typegen`, then `node_modules/.bin/tsc --noEmit -p tsconfig.json`, with T1's flags and X21's. https://nextjs.org/docs/app/api-reference/config/typescript
2. `node_modules/.bin/eslint . --max-warnings 0`, extending `eslint-config-next/core-web-vitals` (Next's rules, React's and the React Hooks set of X6) and the TypeScript tool gate's config and rules, with the `recommended` rules of `eslint-plugin-jsx-a11y` (X15), `react/no-danger` (X16) and `no-restricted-imports` on the component library's package root (X14) at `error`. https://nextjs.org/docs/app/api-reference/config/eslint
3. `node tools/check-tokens.mjs` (X12).
4. `node_modules/.bin/vitest run` (X18). https://vitest.dev/guide/
5. `node_modules/.bin/next build`. https://nextjs.org/docs/app/guides/building
6. `node_modules/.bin/playwright test`, against that build (X18). Its `webServer` runs `next start` on a port kept for the flows, with `reuseExistingServer: false`, so a server already on that port stops the run and is never tested in the build's place. https://playwright.dev/docs/test-webserver

A Vite app runs the same gate with `vite build` at step 5 and no `next typegen`. With no `eslint-config-next`, its lint config registers the React, React Hooks, jsx-a11y and import-x plugins itself; `vite/eslint.config.mjs` in /ground-react's starting files is that config.

## Shared library home in React

A component two apps need lives in one shared package your organization names, its design system where it has one, and is imported, not copied (G2, C4). Where the repo names a design system or brand guidance, a new component follows it and an existing one is used before a new one is written. Starter files are /ground-react's assets.
